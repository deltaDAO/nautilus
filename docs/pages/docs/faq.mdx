# FAQ [Answers to our most frequented questions]

## Why does publishing need a remote store?

Because v2 does not write the DDO on chain. It signs the document as a verifiable
credential, has the node encrypt it, stores it off chain, and writes only an encrypted
`{ remote: … }` pointer that ocean-node dereferences. Without somewhere to put the document
there is nothing to point at, so [`publish`](/docs/api/nautilus/publish) throws.

Use `IpfsRemoteStore` with a Kubo node or a pinning service such as Pinata, or
`S3RemoteStore` with an S3-compatible bucket. The node's own
storage (`NodePersistentRemoteStore`) cannot hold DDOs on ocean-node 4.2, so nautilus
rejects it. See [remote stores](/docs/guides/remote-stores).

## My asset is on chain, but `getAsset` says "DDO not found"

The transactions succeeded, but the node could not index the asset. It does not say so on
chain; it records a failure in its indexing state, under the transaction:

```sh
curl "https://<your-node>/api/aquarius/state/ddo?txId=<setMetadata tx hash, lower-case>"
```

`?nft=<nftAddress>` finds failures too, but a later success does not remove them, so it can
return an old error from an earlier transaction. A **success** is filed under the DID instead
(`?did=did:ope:…`). From nautilus, use
[`getIndexingState`](/docs/guides/ocean-node#indexing-state). With
`waitForIndexer`, nautilus reads it for you and throws an `IndexingError` with the node's
message. Typical causes: the node cannot fetch the remote store's content through its
gateway, the node is not an OceanProtocolEnterprise ocean-node 4.2.x, the publisher key is the
node's own (decrypt then fails with 401; nautilus warns about it), or two metadata
transactions for the asset landed in one block (nautilus then throws a
`MetadataConflictError`).

## Can I publish without encryption?

No. Since 2.0.0-beta.1 nautilus is encrypted only: the stored envelope and the on-chain
pointer are always node-encrypted (flags `0x02`), and `encrypt: false` throws. The DDO is
never written on chain.

## Where did the subgraph go?

Gone, along with the `urql` and `graphql` dependencies. `Config` has no `subgraphUri` at all
any more. Prices are derived from **contract reads** plus the indexed
`indexedMetadata.stats[].prices`, exactly as ocean.js does it.

v1's `getAccessDetails` and `AccessDetails` are replaced by
[`getPricingInfo`](/docs/api/pricing/getPricingInfo) and
[`getOrderPrice`](/docs/api/pricing/getOrderPrice). See [pricing](/docs/guides/pricing).

## Why is my gated asset letting everyone through?

Check whether the node has a policy server (`POLICY_SERVER_URL`). Without one, ocean-node
checks address and access lists itself, and does not know an `SSIpolicy` entry: with
`match_allow: 'any'`, another entry that matches lets the consumer through without the
credentials the `SSIpolicy` asks for. (Under the default `match_allow: 'all'` the unknown
entry denies everyone instead.)

`initializePolicyVerification` returning `null`, or `hasPolicyServer()` answering `false`,
says the node has no policy server. This is a deployment property, not something nautilus
can compensate for.

:::warning
Publish-time policy enforcement does not exist yet either — the policy server's `newDDO`,
`updateDDO`, `validateDDO`, `encrypt` and `decrypt` actions are stubs that always allow.
Credential gating is enforced on **consumption**, not on publication.
:::

## Which wallet do I need for a node with the native SSI module?

walt.id **wallet-api2**, through
[`WalletApi2CredentialProvider`](/docs/api/identity/WalletApi2CredentialProvider). A node
with the native SSI module sends an OpenID4VP 1.0 request with a DCQL query, which walt.id's
v1 wallet API cannot answer: [`WaltIdCredentialProvider`](/docs/api/identity/WaltIdCredentialProvider)
refuses it with a `CredentialPresentationError` (`reason: 'request-invalid'`), and keeps
working for nodes with a policy server. To see which kind a node is, call
[`getSsiCapabilities(nodeUri)`](/docs/api/nautilus/getSsiCapabilities): an object for a node
that announces the module (`status.ssi`), `null` for one that does not, `undefined` when its
status cannot be read.

## Why is my consumer getting HTTP 429 from `ssiInitiate`?

The node limits how many SSI sessions may be pending (opened, not yet verified, presentation
window still open) at once: by default 5 per consumer address, with further caps per client,
per asset and per node. A session that is opened and never presented counts until its window
closes (`challenge.expiresAt`, when the node sends it), so repeated attempts that fail after
`ssiInitiate` use up the allowance. A credential provider can check what it can before the
session is opened, in the optional
[`prepare()`](/docs/api/identity/CredentialProvider): `WalletApi2CredentialProvider` resolves
the consumer's wallet there, so a missing wallet or a rejected token throws a
`wallet-setup` error and leaves no pending session. Otherwise wait for the pending sessions
to expire.

## Can I mix Gaia-X and W3C credential queries?

Not in one `SSIpolicyV2` value. The wallet signs all W3C credentials of one presentation with
the organisation's `did:web`, so a value that asks for Gaia-X compliance cannot also have a
W3C query (`jwt_vc_json`): [`addSsiPolicyV2`](/docs/api/assetbuilder/addSsiPolicyV2) throws an
`SsiPolicyValidationError`, and the node refuses such a value with a 422. Ask for the other
credentials as `dc+sd-jwt`, or put them in another `SSIpolicyV2` value.

## Which credential formats can an `SSIpolicyV2` ask for?

`jwt_vc_json`, `dc+sd-jwt` and `vc+sd-jwt`; anything else is refused when the value is added.
`dc+sd-jwt` credentials are bound to the consumer by the node's `transaction_data`;
`jwt_vc_json` credentials only with `consumerBinding: true` (see
[credential-gated assets](/docs/guides/identity#nodes-with-the-native-ssi-module)).

## A rego deny shows as the VC policy `dynamic`

verifier-api2 runs an asset's rego as the credential policy `dynamic`, so a
`PolicyDeniedError` for a rego deny has a failed `policyResults` entry with `scope: 'vc'` and
`policy: 'dynamic'` (`credential`: the DCQL query id). Check rego before publishing with
[`validateRego`](/docs/api/nautilus/validateRego), which compiles it in the node's verifier.

## Why am I paying twice for the same asset?

[`access`](/docs/api/nautilus/access) reuses your previous order while it is inside the
service's timeout. ocean-node 3.0 to 4.2 report no `validOrder` from the access
`initialize`, so nautilus finds the order in the datatoken's events instead, reading back
no further than the timeout and at most 100 000 blocks. An order past its timeout, or one
placed by another account or for another service, means a new order. `reusedOrder` in the
result says which happened. A lookup the RPC refuses, or one that cannot read back over the
whole timeout, does not buy a service that costs anything: `access()` throws an
[`OrderCheckError`](/docs/api/nautilus/access#ordercheckerror) before paying, unless you
pass `orderOnLookupFailure: true`.

[`compute`](/docs/api/nautilus/compute) orders each input on every job. See
[Do you already hold an order?](/docs/guides/pricing#do-you-already-hold-an-order).

## Never put `127.0.0.1` in a DDO

ocean-node's `DEFAULT_UNSAFE_URLS` blocks any URL matching it, and the failure surfaces as
"URL is marked as unsafe" rather than a connection error — which sends people looking in the
wrong place entirely.

Use a hostname the **node** can resolve. Remember that *you* never fetch these URLs; the node
does, to encrypt the files object at publish time.

## Free compute vs. paid compute

[`freeCompute`](/docs/api/nautilus/freeCompute) places no order, funds no escrow and takes no
payment token. It needs a compute environment that exposes free resources — if none does, the
call fails and there is nothing to configure your way out of.

[`compute`](/docs/api/nautilus/compute) orders every input, locks funds in the chain's
escrow contract (its `EnterpriseEscrow` by default) from what the node quotes, and then
starts the job.

## Why does `build()` reject my asset?

DDO v5 requires `providedBy`, which had no v4 equivalent, so assets ported from v1 fail on a
field that did not used to exist. `build()` also requires `name`, `type`, and at least one
service — and container metadata when `type` is `'algorithm'`.

Everything beyond that is checked by [`validate`](/docs/guides/validation), which
`publish()` runs automatically before spending any gas.

## Do I still need separate Aquarius and Provider URLs?

No. One **ocean-node** serves metadata, provider services and the indexer, so
`metadataCacheUri` and `providerUri` both collapse into a single `oceanNodeUri`. See
[migrating from v1](/docs/migration).
