# setSsiPolicyLint

Choose what [`build()`](/docs/api/assetbuilder/build) does when the asset's SSI policies
check less than they seem to, or refuse common credentials.

`build()` checks the `SSIpolicy` of the asset and of every service the built asset will have
(on an edit, the published services it keeps too), the way the policy server merges them for
a service. It warns when:

| Event | When |
| --- | --- |
| `identity.policy.holder_binding` | `holder-binding` is among the VP policies. It requires every credential's JWT `sub` to be the presenter's DID, so it refuses Gaia-X and other VCDM 2.0 `vc+jwt` credentials with a URL subject. |
| `identity.policy.presentation_definition_vc_jwt` | `presentation-definition` is combined with a `jwt_vc_json` (or `jwt_vc`) request credential. walt.id's generated definition looks for the type at `$.vc.type`, which VCDM 2.0 credentials do not have. |
| `identity.policy.no_issuer_trust` | A requested credential type has no per-credential `allowed-issuer` among the policies walt.id runs for it (the last non-empty list for the type, after the policy server drops repeats of an identical request), so a credential of that type from any issuer, a self-issued one included, is accepted. |
| `identity.policy.issuer_not_did` | A stored per-credential `allowed-issuer` lists an entry that is not a DID, next to a usable one. walt.id compares the credential's `iss` with each entry as written, so it trusts only an issuer whose `iss` is exactly that text. |
| `identity.policy.weak_schema` | A per-credential `schema` checks less than it seems, judged in the JSON Schema dialect walt.id's validator uses: the one its `$schema` names, or 2020-12 without one (walt.id's own description says draft 7, but its validator applies 2020-12). Reported: keys that dialect does not define (walt.id ignores them; e.g. the credential's own shape pasted as a schema, a misspelled `required`, or draft 7's `dependencies` without a draft-07 `$schema`), keys next to `$ref` under draft 4 to 7 (ignored there), no constraint at all, an attribute under `properties` that its level's `required` does not list (a credential without it passes), and a `$schema` walt.id's validator does not support or an `items` list under 2020-12 (either fails every presentation). Schemas from [`requireCredentialAttributes`](/docs/api/assetbuilder/requireCredentialAttributes) never warn. |
| `identity.policy.format_ignores_type` | A request credential with per-credential policies has the format `vc+sd-jwt` or `mso_mdoc`. walt.id's presentation definition for these formats does not ask for the requested type (any `vct`; fixed mDL fields), so a wallet that presents a credential of another type for the request skips the policies. Use `jwt_vc_json`. |
| `identity.policy.unknown_name` | A VC, VP or per-credential policy name is not one walt.id knows (90e568f). A verifier that does not know it fails every presentation; a newer one may know it. |
| `identity.policy.no_vc_signature` | A credential-gated service's VC policies (asset and service merged) have no `signature`: a credential that names a trusted issuer but is signed by anyone passes `allowed-issuer`. |
| `identity.policy.no_vp_signature` | A credential-gated service's VP policies have no `signature`: nothing is sure to check the presentation's own signature. |
| `identity.policy.no_minimum_credentials` | A credential-gated service's VP policies have no `minimum-credentials` of at least 1: a presentation holding no credential passes. |
| `identity.policy.wildcard_allow` | A credential-gated service lets every address in (`'*'` in the allow list, read as the policy server reads it), so a hand-built presentation of another credential type opens it to anyone ([type bypass](/docs/guides/identity#known-limitation-credentials-of-another-type)). |

The policy server may add `signature` from its operator's `DEFAULT_VC_POLICIES` /
`DEFAULT_VP_POLICIES`, which nautilus cannot read; list it on the asset or service so the
check holds whatever the operator set. The recommended set
([identity guide](/docs/guides/identity#publishing-a-gated-asset)) builds without a warning.

Each event carries `where` (`'asset'` or `'service <id or name>'`, the place the policy sits or,
for a missing one, where the service's policies sit) and, where it applies, `credentialType`; `identity.policy.unknown_name` also carries `policy`.
Service ids and names are sanitised (control characters stripped, length bounded); on an
edit they come from the node.

## Usage

```ts twoslash
import { AssetBuilder } from '@deltadao/nautilus'

const assetBuilder = new AssetBuilder()
// ---cut---
assetBuilder.setSsiPolicyLint('error') // [!code focus]
```

## Parameters

### mode

- Type: `'warn' | 'error' | 'off'`

- `'warn'` (the default): each finding is logged as a `warn` event. Existing assets keep
  building.
- `'error'`: `build()` throws an `SsiPolicyError` whose `findings` list them all, the fatal
  ones (below) first. Its message spells out the first 20.
- `'off'`: no warnings. A fatal finding still throws, with only the fatal ones in
  `findings`.

In `'warn'` mode a fatal finding throws as well, and its `SsiPolicyError.findings` then holds
the warnings too, which are not logged.

Any other value throws a `TypeError`. The mode is kept across [`reset()`](/docs/api/assetbuilder/reset).

:::warning[Some setups throw in every mode]
`build()` throws an `SsiPolicyError` whatever the mode for policies that cannot work as
written:

- `no-request-credentials`: a service whose merged view (asset and service) holds an
  `SSIpolicy` entry but requests no credential. The policy server refuses every consumer of
  it ("SSIpolicy was found, but failed to fetch request credentials"). Typical cause: VC or VP
  policies on the asset next to a service without request credentials. Put the policies on the
  gated service with [`ServiceBuilder.setVcPolicies`](/docs/api/servicebuilder/setVcPolicies)
  and [`setVpPolicies`](/docs/api/servicebuilder/setVpPolicies), or add request credentials;
- `vc-policy-arguments`: a VC policy at asset or service level that needs arguments
  (`allowed-issuer`, `schema`, `webhook`, `dynamic`, `credential-status`): the policy server
  keeps only the name, so walt.id fails it for every presentation. Put it on the credential, in
  the `policies` of [`addRequestCredentials`](/docs/api/assetbuilder/addRequestCredentials).
  Any other VC policy with arguments (`{ policy: 'expired', args }`) runs without them, a
  different check: drop the arguments and keep the name, which checks every presented
  credential (moving it onto one credential would check only credentials of that type);
- `vp-policy-arguments`: `minimum-credentials` or `maximum-credentials` without an integer
  argument (`args: '1'`), or `vp_required_credentials` without one of the form
  `JSON.stringify({ required: [{ credential_type: '<type>' }] })`: walt.id fails it for every
  presentation;
- `credential-policy-arguments`: a per-credential `allowed-issuer` that names no issuer (no
  `args`, `[]`, `'*'`; `'*'` is not a wildcard in walt.id), or a per-credential `schema` whose
  `args` are not a JSON Schema object: walt.id fails it for every presentation;
- `credential-policies-replaced`: a type requested more than once, at asset and service level
  merged, where a non-empty per-credential list is dropped. walt.id keeps only the last
  non-empty list per type, after the policy server drops repeats of an identical request (the
  first one keeps its position), so a check you configured, e.g. issuer trust, never runs. A
  request of the type without policies next to one with policies is fine. Put all of a type's
  policies on one request: [`trustIssuers`](/docs/api/assetbuilder/trustIssuers) and
  [`requireCredentialAttributes`](/docs/api/assetbuilder/requireCredentialAttributes) add to
  it;
- `generic-request-type`: per-credential policies on `VerifiableCredential` or
  `VerifiablePresentation`. walt.id files a presented credential under the last entry of its
  `type`, so they never run on a credential with a more specific type, which a wallet still
  presents. Request the credentials' own type, the last entry of their `type` array;
- `request-format`: request credentials without a format, with different formats (one type
  in two formats included), or with one walt.id does not request. walt.id refuses to open the
  session ("Credentials formats must be distinct for a presentation request"), and so every
  consumer.
:::

:::info
The warnings go to the process-wide logger ([`configureLogging`](/docs/api/nautilus/configureLogging)),
not to a `Nautilus` instance's own: the builder has none. The lint does not close the
[type bypass](/docs/guides/identity#known-limitation-credentials-of-another-type): it checks
what the asset asks for, not what a hand-built presentation sends.
:::

## Returns

- Type: [`AssetBuilder`](/docs/api/AssetBuilder)

The asset builder instance, to chain further calls with.
