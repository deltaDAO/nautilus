# requireCredentialAttributes

Require attributes of a requested credential: for example, only `gx:LegalPerson` credentials
whose `gx:legalAddress.gx:countryCode` is `DE`.

It writes walt.id's per-credential `schema` policy on the `allow` list, a JSON Schema built
from the requirements, and adds the request credential if it is not there yet. See
[Requiring credential attributes](/docs/guides/identity#requiring-credential-attributes).

## Usage

```ts twoslash
import { AssetBuilder } from '@deltadao/nautilus'

const assetBuilder = new AssetBuilder()
// ---cut---
assetBuilder
  .trustIssuers('gx:LegalPerson', ['did:web:delta-dao.com'])
  .requireCredentialAttributes('gx:LegalPerson', [ // [!code focus]
    { path: ['gx:legalAddress', 'gx:countryCode'], equals: 'DE' } // [!code focus]
  ]) // [!code focus]
```

The generated schema for that requirement:

```json
{
  "type": "object",
  "required": ["credentialSubject"],
  "properties": {
    "credentialSubject": {
      "type": "object",
      "required": ["gx:legalAddress"],
      "properties": {
        "gx:legalAddress": {
          "type": "object",
          "required": ["gx:countryCode"],
          "properties": { "gx:countryCode": { "const": "DE" } }
        }
      }
    }
  }
}
```

walt.id checks it against the credential's `vc` claim (VCDM 1.1), or the JWT payload when there
is none (VCDM 2.0 `vc+jwt`). Both have `credentialSubject` at the root, so the same schema
serves both. `credentialAttributeSchema(requirements)` returns it without changing a builder.

## Parameters

### type

- Type: `string`

The credential type, as in `request_credentials`, e.g. `'gx:LegalPerson'`.

### requirements

- Type: `CredentialAttributeRequirement[]`

Each one is `{ path, equals?, oneOf?, exists? }`, with at most one of the last three:

| Field | Type | Meaning |
| --- | --- | --- |
| `path` | `string[]` | The keys from `credentialSubject` down to the attribute |
| `equals` | `string \| number \| boolean` | The attribute must be this value (`const`) |
| `oneOf` | `(string \| number \| boolean)[]` | The attribute must be one of these (`enum`) |
| `exists` | `true` | The attribute must exist, with any value. Also what a requirement without a condition means |

All requirements must hold. Requirements on the same path combine: `oneOf: ['DE', 'AT']` and
`equals: 'DE'` give `DE`. Contradictory requirements (`equals: 'DE'` and `equals: 'FR'`, or an
attribute required both to have a value and to hold others), an empty path, the path segments
`__proto__`, `constructor` and `prototype`, and values that are not strings, finite numbers or
booleans throw a `TypeError`.

### options

- Type: `{ format?: string }`

Which request credential to change. Without `format`, the one request for `type` already on
the list, or else a new `jwt_vc_json` one.

## Combining

Calls add to the same request credential: their requirements combine with AND, and so do the
requirements of a `schema` policy already there. A hand-written schema that is not in the
generated form is kept, combined as `{ allOf: [existing, added] }`. One whose `args` are not
an object throws a `TypeError`: replace it with
[`setRequestCredentials`](/docs/api/assetbuilder/setRequestCredentials).

The stored policies are ordered issuer trust first, then the schema, then any others, so the
stored form does not depend on the order of the calls.

walt.id keeps one per-credential policy list per credential type, so request each type once:
[`build()`](/docs/api/assetbuilder/build) throws an `SsiPolicyError` when a type is requested
twice with different policies, at asset and service level merged.

:::warning[Only credentials of the requested type are checked]
walt.id runs per-credential policies only on presented credentials whose type (the last entry
of `type`) is the requested one. A hand-built presentation holding a self-issued credential of
another type skips the attribute check and the issuer check. The requirement filters honest
consumers, whose wallet presents only the requested type; it is not access control against
someone who builds their own presentation. Keep an explicit address allow list. See the
[known limitation](/docs/guides/identity#known-limitation-credentials-of-another-type).
:::

## Consumers

`WaltIdCredentialProvider` checks the selected credentials against these requirements before
presenting, and throws a `CredentialRejectedLocallyError` with `reason: 'attribute-mismatch'`
and the failing `path` for one the verifier would refuse. See
[Refused before presenting](/docs/guides/identity#refused-before-presenting).

## Returns

- Type: [`AssetBuilder`](/docs/api/AssetBuilder)

The asset builder instance, to chain further calls with.
