# setVpPolicies

Set the checks applied to the presentation as a whole.

Where VC policies check individual credentials, these check the presentation as a whole, for example that it carries enough credentials (`minimum-credentials`).

Each policy is an object: `{ policy }`, or `{ policy, args }` for a parameterised one. An asset whose `vp_policies` mixed names and objects was not indexed by ocean-node 4.2.x, so nautilus writes objects only, as the enterprise market does. `args` is a string; the policy server parses it as JSON when it can (`'1'` reaches the verifier as `1`), so pass structured arguments through `JSON.stringify`.

## Usage

```ts twoslash
import { AssetBuilder } from '@deltadao/nautilus'

const assetBuilder = new AssetBuilder()
// ---cut---
import { CredentialListTypes } from '@deltadao/nautilus'

assetBuilder.setVpPolicies(CredentialListTypes.ALLOW, [ // [!code focus]
  { policy: 'signature' }, // [!code focus]
  { policy: 'minimum-credentials', args: '1' } // [!code focus]
]) // [!code focus]
```

`minimum-credentials` needs an integer argument: a bare `{ policy: 'minimum-credentials' }`
(or `args: 'abc'`) fails in the walt.id verifier for every presentation, so
[`build()`](/docs/api/assetbuilder/build) throws an `SsiPolicyError` for it, and for
`maximum-credentials` likewise. `vp_required_credentials` takes an object,
`args: JSON.stringify({ required: [{ credential_type: 'gx:LegalPerson' }] })`; `build()`
throws for any other shape. Without a `minimum-credentials` of at least 1, a presentation
holding no credential passes: `build()` warns `identity.policy.no_minimum_credentials`.

The policy server merges these into every service of the asset, and refuses every consumer of
a service that then holds an `SSIpolicy` entry but requests no credential: when one service
stays open, set them on the gated service with
[`ServiceBuilder.setVpPolicies`](/docs/api/servicebuilder/setVpPolicies).

**Check the presentation's own signature** with `{ policy: 'signature' }` among the VP
policies. walt.id runs only the VP policies the session lists, so without it nothing checks
that the presentation was signed by the DID it names, unless the policy server's operator adds
it through `DEFAULT_VP_POLICIES`, which nautilus cannot see. Listed on the asset, the check
holds whatever that setting is; when the policy server adds it too, it simply runs twice. It
does not bind the credential to the presenter, which is `holder-binding`'s job, and it does not
stop a presentation replayed from an earlier session: the verifier accepts it. Without it,
`build()` warns `identity.policy.no_vp_signature`.

:::warning[`holder-binding` and `presentation-definition`]
Neither belongs in the default set:

- `holder-binding` reads the credential JWT's `sub` and fails (a `NullPointerException` in
  walt.id) for credentials without `sub` (common for VCDM 2.0 `vc+jwt`) and URL-subject
  credentials such as Gaia-X `gx:LegalPerson`. Where it does work, it binds a credential to
  its presenter only with the presentation's signature verified (the VP policy `signature`
  above), since it compares `sub` with the DID the presentation claims. Without it a copied
  credential can be presented from any wallet, so bind access to an account with the address
  allow list.
- `presentation-definition` refuses VCDM 2.0 `vc+jwt` credentials, because the definition
  walt.id generates for `jwt_vc_json` matches the type at `$.vc.type`, which they do not have.

[`build()`](/docs/api/assetbuilder/build) warns about both (see
[`setSsiPolicyLint`](/docs/api/assetbuilder/setSsiPolicyLint)). See
[the identity guide](/docs/guides/identity#choosing-vp-and-vc-policies) for the recommended
policies and why.
:::

:::info
On an asset built from a resolved DDO, VP policies stored as bare names (by an earlier
nautilus) are rewritten as objects when the edit is published.
:::

:::info
This *replaces* the list. On an asset built from a resolved DDO, the policies you pass are
the policies it ends up with — leaving one out removes it, and `[]` clears them. The request
credentials on the entry are kept either way. An `SSIpolicy` entry left with no request
credential and no VC or VP policy is removed: on an edit of an asset with an ungated service,
`setVcPolicies(list, []).setVpPolicies(list, [])` clears the asset-level gate, so the
policies can move onto the gated service with
[`ServiceBuilder.setVcPolicies`](/docs/api/servicebuilder/setVcPolicies) and
[`setVpPolicies`](/docs/api/servicebuilder/setVpPolicies).
:::
