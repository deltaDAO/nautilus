# setVpPolicies

Set the checks applied to the presentation as a whole.

Where VC policies check individual credentials, these check the presentation as a whole, for example that it carries enough credentials (`minimum-credentials`).

Each policy is an object: `{ policy }`, or `{ policy, args }` for a parameterised one. An asset whose `vp_policies` mixed names and objects was not indexed by ocean-node 4.2.x, so nautilus writes objects only, as the enterprise market does. `args` is a string; the policy server parses it as JSON when it can (`'1'` reaches the verifier as `1`), so pass structured arguments through `JSON.stringify`.

## Usage

```ts twoslash
import { AssetBuilder } from '@deltadao/nautilus'

const assetBuilder = new AssetBuilder()
// ---cut---
import { CredentialListTypes } from '@deltadao/nautilus'

assetBuilder.setVpPolicies(CredentialListTypes.ALLOW, [ // [!code focus]
  { policy: 'minimum-credentials', args: '1' } // [!code focus]
]) // [!code focus]
```

`minimum-credentials` needs its argument: a bare `{ policy: 'minimum-credentials' }` fails in
the walt.id verifier for every presentation.

:::warning[`holder-binding` and `presentation-definition`]
Neither belongs in the default set:

- `holder-binding` reads the credential JWT's `sub` and fails (a `NullPointerException` in
  walt.id) for credentials without `sub` (common for VCDM 2.0 `vc+jwt`) and URL-subject
  credentials such as Gaia-X `gx:LegalPerson`. Where it does work, it binds a credential to
  its presenter only with the presentation's signature verified (the VP policy `signature`),
  since it compares `sub` with the DID the presentation claims. Without it a copied
  credential can be presented from any wallet, so bind access to an account with the address
  allow list.
- `presentation-definition` refuses VCDM 2.0 `vc+jwt` credentials, because the definition
  walt.id generates for `jwt_vc_json` matches the type at `$.vc.type`, which they do not have.

See [the identity guide](/docs/guides/identity#publishing-a-gated-asset) for the recommended
policies and why.
:::

:::info
On an asset built from a resolved DDO, VP policies stored as bare names (by an earlier
nautilus) are rewritten as objects when the edit is published.
:::

:::info
This *replaces* the list. On an asset built from a resolved DDO, the policies you pass are
the policies it ends up with — leaving one out removes it, and `[]` clears them. The request
credentials on the entry are kept either way.
:::

## Returns

- Type: [`AssetBuilder`](/docs/api/AssetBuilder)

The asset builder instance, to chain further calls with.
