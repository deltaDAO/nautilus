# setVcPolicies

Set the checks applied to each presented credential.

nautilus's `DEFAULT_VC_POLICIES` are `signature`, `not-before` and `revoked-status-list`, the values the policy server ships in its `default-verification-policies` file. A deployment can run more: the policy server adds the `DEFAULT_VC_POLICIES` and `DEFAULT_VP_POLICIES` of its environment to every session, which nautilus cannot see. Valid names can be enumerated from the walt.id verifier's `/openid4vc/policy-list` endpoint.

## Usage

```ts twoslash
import { AssetBuilder } from '@deltadao/nautilus'

const assetBuilder = new AssetBuilder()
// ---cut---
import { CredentialListTypes } from '@deltadao/nautilus'

assetBuilder.setVcPolicies(CredentialListTypes.ALLOW, [ // [!code focus]
  'signature', // [!code focus]
  'not-before', // [!code focus]
  'revoked-status-list' // [!code focus]
]) // [!code focus]
```

:::warning[Arguments are dropped at this level]
These are names only. The policy server keeps only the *name* of an asset- or service-level
VC policy and drops any arguments, so a policy that needs one fails in the verifier:
`allowed-issuer` without its issuers throws "Invalid argument", which fails every
presentation and denies every consumer. Put argument-bearing policies, such as issuer trust
(`allowed-issuer`) or walt.id's `schema`, on the credential instead, in the `policies` of
[`addRequestCredentials`](/docs/api/assetbuilder/addRequestCredentials).

[`build()`](/docs/api/assetbuilder/build) throws an `SsiPolicyError` for such a list: any
entry with arguments, and `allowed-issuer`, `schema`, `webhook`, `dynamic` or
`credential-status`, which cannot work without them. For another policy with arguments, such as
`{ policy: 'expired', args }`, drop the arguments and keep the name here: moving it onto one
credential would check only credentials of that type.
:::

:::warning[Not next to an ungated service]
The policy server merges these into every service of the asset, and refuses every consumer of
a service that then holds an `SSIpolicy` entry but requests no credential. When one service
stays open, set the policies on the gated service instead, with
[`ServiceBuilder.setVcPolicies`](/docs/api/servicebuilder/setVcPolicies); `build()` throws for
the asset-level form. Without `signature` in the list, `build()` warns
`identity.policy.no_vc_signature`.
:::

:::info
This *replaces* the list. On an asset built from a resolved DDO, the policies you pass are
the policies it ends up with — leaving one out removes it, and `[]` clears them. The request
credentials on the entry are kept either way. An `SSIpolicy` entry left with no request
credential and no VC or VP policy is removed: on an edit of an asset with an ungated service,
`setVcPolicies(list, []).setVpPolicies(list, [])` clears the asset-level gate, so the
policies can move onto the gated service with
[`ServiceBuilder.setVcPolicies`](/docs/api/servicebuilder/setVcPolicies) and
[`setVpPolicies`](/docs/api/servicebuilder/setVpPolicies).
:::
