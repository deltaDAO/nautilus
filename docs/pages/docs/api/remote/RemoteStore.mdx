# RemoteStore

The interface every remote store implements. One required method, `put`, and three optional
ones: `check`, `verify` and `remove`.

```ts twoslash
import type { RemoteStore } from '@deltadao/nautilus'
import type { StorageObject } from '@oceanprotocol/lib'
// ---cut---
class MyStore implements RemoteStore {
  async put(payload: string, hint: { did: string }): Promise<StorageObject> { // [!code focus]
    const url = await upload(payload, `${hint.did}.json`)

    return { type: 'url', url, method: 'GET' } as StorageObject
  }
}

declare function upload(body: string, name: string): Promise<string>
```

## put

### Parameters

#### payload

- Type: `string`

The **encrypted DDO envelope**, a JSON string `{"encryptedData":"0x…"}` whose value is node
ciphertext. It is not the signed DDO: nothing readable reaches the store.

Store it **unchanged**. Its sha256 is the on-chain `metaDataHash`, and the node recomputes
that hash over what it fetches (after `JSON.parse` and `JSON.stringify`, so added whitespace is
harmless). Wrapping the payload, re-encoding it or adding fields breaks indexing. See
[what is stored](/docs/guides/remote-stores#what-is-stored).

#### hint

- Type: `{ did: string }`

A stable name derived from the DID, for stores that need a key.

### Returns

- Type: `Promise<StorageObject>`

A pointer the **node** can dereference:

| `type` | shape |
| --- | --- |
| `ipfs` | `{ type, hash }` |
| `url` | `{ type, url, method }` |
| `arweave` | `{ type, transactionId }` |
| `s3` | `{ type, s3Access }` |
| `ftp` | `{ type, url }` |

nautilus wraps it in `{ remote: … }` and has the node encrypt it before writing it on chain.
The wrapper must carry exactly one key or the node will not treat it as a remote DDO.

nautilus validates the pointer before anything goes on chain, for every store (the `type` is
matched case-insensitively). It rejects a `nodePersistentStorage` pointer — ocean-node 4.2 cannot read a remote DDO from its own bucket
storage, see [`NodePersistentRemoteStore`](/docs/api/remote/NodePersistentRemoteStore) — any
other type not in the table, an `ipfs` pointer whose `hash` is not a CIDv0 (`Qm…`) or a
base32/base36 CIDv1 (`b…`/`k…`), and a pointer that is not a plain JSON object or is already
wrapped in `{ remote }`. See [storage options](/docs/guides/remote-stores#storage-options) for
what each type needs on the node.

## check (optional)

- Type: `() => Promise<void>`

A preflight that [`publish`](/docs/api/nautilus/publish),
[`completePublish`](/docs/api/nautilus/completePublish) and [`edit`](/docs/api/nautilus/edit)
call **before their first transaction**. The NFT has to exist before the DDO can be stored,
because the DID derives from its address, so a store that fails only at `put` leaves an NFT
without metadata (or, on an edit, datatokens minted for nothing). Throw here if you can tell
up front that `put` will fail: bad credentials, missing scopes, an unreachable endpoint.

```ts twoslash
import type { RemoteStore } from '@deltadao/nautilus'
import type { StorageObject } from '@oceanprotocol/lib'

declare function upload(body: string, name: string): Promise<string>
declare function ping(): Promise<boolean>
// ---cut---
class MyStore implements RemoteStore {
  async put(payload: string, hint: { did: string }): Promise<StorageObject> {
    const url = await upload(payload, `${hint.did}.json`)

    return { type: 'url', url, method: 'GET' } as StorageObject
  }

  async check(): Promise<void> { // [!code focus]
    if (!(await ping())) throw new Error('store unreachable') // [!code focus]
  } // [!code focus]
}
```

## verify (optional)

- Type: `(pointer: StorageObject, expectedHash: string) => Promise<void>`

A read-back that `publish`, `completePublish` and `edit` call after `put()` and **right before
the metadata transaction**, with the pointer exactly as `put()` returned it (not redacted).
Read the object behind `pointer` the way the node will — with the credentials the pointer
carries — and throw unless `"0x" + sha256(JSON.stringify(JSON.parse(body)))` equals
`expectedHash`, which is exactly the node's check.

On ocean-node 4.2 a `MetadataCreated` the node could not index cannot be repaired by
nautilus — `completePublish` refuses an NFT that has metadata, and `edit` needs the indexed
asset — so catching a store that alters bytes, or a key the node
cannot read with, before the transaction is worth the round trip. Stores without `verify` are
not verified. `S3RemoteStore` implements it with the read key; `IpfsRemoteStore` does when
its `gatewayUrl` is set.

## remove (optional)

- Type: `(pointer: StorageObject) => Promise<void>`

Deletes what a pointer from `put()` refers to, for cleanup. It must work with the
**redacted** pointer from [`PublishResponse.stored`](/docs/api/PublishResponse#stored), whose
secrets read `'<redacted>'`.
[`S3RemoteStore`](/docs/api/remote/S3RemoteStore#remove) deletes the object;
[`IpfsRemoteStore`](/docs/api/remote/IpfsRemoteStore#remove) unpins the CID.

nautilus calls it in one case only: `publish`, `completePublish` or `edit` stored the envelope
and then failed **before the metadata transaction was sent** (a failed `verify`, a pointer the
node would not encrypt, a transaction that could not be built). Nothing can point at that
object, so it is removed, best effort; the outcome is on
[`error.stored`](/docs/guides/remote-stores#when-a-write-fails-after-the-envelope-is-stored).
Once the transaction may have been sent, nautilus never removes anything. Cleaning up is up
to you, and an asset that should stay indexed needs two envelopes for good: the **creation**
one (from `publish()`), because a node reindex replays the asset from its creation event and
drops it from the index when that envelope is gone, and the **current** one. Intermediate
versions and those of assets retired for good can go; see
[cleaning up](/docs/guides/remote-stores#cleaning-up).
