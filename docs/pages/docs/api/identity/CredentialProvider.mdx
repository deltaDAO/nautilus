# CredentialProvider

The interface nautilus calls to answer a verifiable-presentation request. One method.

nautilus opens the policy-server session itself ([`PolicySessionResolver`](/docs/api/identity/PolicySessionResolver)):
it starts the verification, reads the session id and, after the presentation, checks that the
verifier accepted it. A provider does only the step in between: answering the openid4vp
request from a wallet. It is called only for a service whose `SSIpolicy` asks for
credentials; a service gated by addresses only needs no provider.

```ts twoslash
import type { CredentialProvider, CredentialChallenge } from '@deltadao/nautilus'
// ---cut---
class MyProvider implements CredentialProvider {
  async present(challenge: CredentialChallenge): Promise<void> { // [!code focus]
    challenge.asset
    challenge.serviceId
    challenge.consumerAddress
    challenge.node // the node that opened the session and will enforce it
    challenge.sessionId // the session the policy server opened
    challenge.redirectUri // the openid4vp request to answer
  }
}
```

Resolve once the verifier has the presentation. Throw only when you could not present at all
(no matching credential, a rejected request): whether the verifier accepted it is checked by
nautilus afterwards, and a presentation it did not accept is a `PolicyDeniedError`.

When `present()` throws, nautilus asks the verifier's record of the session which policies
failed. If it names some, the caller gets a `PolicyDeniedError` with them and your error as its
`cause`; otherwise your error as you threw it. To skip that read when your provider failed
before the verifier saw anything, throw a `CredentialPresentationError` with a `reason` other
than `'verifier-rejected'` (e.g. `'no-matching-credential'`). Keep the session id, the openid4vp request and
the wallet's redirect URI out of your error's message and fields: the session id is a
credential, and apps log errors.

:::warning
Ask `challenge.node` for anything about the session, such as the presentation definition, not a
node of your own. A session is only known to the policy server behind the node that opened it:
for a download that is the node in the service's `serviceEndpoint`, which need not be the one
you configured, and for a compute job it is the node running the job.
:::

## Nodes with the native SSI module

On a node with the native SSI module the challenge has `protocol: 'oid4vp'`: `redirectUri` is
an OpenID4VP 1.0 request (`openid4vp://`), with the node's DCQL query in `challenge.dcql`, the
end of the presentation window in `challenge.expiresAt` and the node's verifier host in
`challenge.verifierHost`. nautilus checks the result with the node's `ssiStatus`. A provider
that speaks only one protocol throws a `CredentialPresentationError` with reason
`'request-invalid'` for the other.

An optional `prepare(context)` runs before nautilus opens the session (`ssiInitiate`). Throw
there when you can already tell you cannot present for `context.consumerAddress` (no wallet,
no login), and no session is opened. A session that is opened and never presented stays
pending at the node until its window closes, and the node allows a consumer only 5 pending
sessions by default.

The session is always opened **before** anything is ordered, so a policy you cannot satisfy
costs you nothing. See [credential-gated assets](/docs/guides/identity).
