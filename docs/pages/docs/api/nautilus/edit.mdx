# edit

Republish an asset with changed metadata, services or credentials.

## Usage

```ts twoslash
import { AssetBuilder, Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
// ---cut---
const asset = await nautilus.getAsset('did:ope:2a6ebce0af...')

const edited = new AssetBuilder(asset) // [!code focus]
  .setName('A better name') // [!code focus]
  .build() // [!code focus]

const { ddo } = await nautilus.edit(edited) // [!code focus]
```

The builder must be constructed **from a resolved asset** — that is what supplies the
baseline to merge over. Passing a freshly built asset throws.

:::info
The merge is structural, not top-level. Setting one field leaves every other field of the
published document intact, so you never have to resupply metadata you are not changing.
:::

Indexer-derived fields — `datatokens`, `event`, `stats`, and anything a client decorated the
asset with — are stripped before signing, so a republish cannot bake in a stale snapshot of
chain state.

Only services carrying a **new pricing config** get a new datatoken. Everything else is
merged over the published services by id. A service whose files or endpoint changed gets a
new id, because the id is the hash of the encrypted file object; nautilus removes the old
entry so the two do not linger side by side.

Like [`publish`](/docs/api/nautilus/publish), the edited DDO is signed, node-encrypted into
an envelope and stored in the remote store, and only the encrypted pointer is written on
chain.

Before any datatoken is minted, `edit()` runs the remote store's `check()`, like `publish()`.
After `put()` and right before the metadata transaction it runs the store's `verify()`, when
the store has one, which reads the stored envelope back and checks its hash. A store that
still fails during an edit leaves the published version in place, but any datatokens already
created for re-priced services stay behind: the error names them as `error.datatokens`.

Within one instance, `edit()` waits for any `publish()`, `completePublish()`, `edit()` or
`setAssetLifecycleState()` of the same NFT still running, but it does **not** wait for the
previous change to be indexed. ocean-node indexes only the first metadata event of an asset
per block, so when another metadata transaction for the NFT landed in the same block (from
another instance or process), `edit()` throws a `MetadataConflictError` — see
[one metadata event per block](/docs/guides/edit#one-metadata-event-per-block).

`edit()` refuses `encrypt: false` and, before anything is spent, a signer without the NFT's
`updateMetadata` permission (and `deployERC20`, when a re-priced service needs a datatoken),
an asset whose NFT is `DEPRECATED` or `REVOKED_BY_PUBLISHER` (read under the same per-NFT
lock, so a revoke this instance started first is seen), and an edit that sets either state
through
[`setLifecycleState`](/docs/api/assetbuilder/setLifecycleState): ocean-node does not decrypt or
index metadata for such an asset, and both states are one-way. Use
[`setAssetLifecycleState`](/docs/api/nautilus/setAssetLifecycleState) to move an asset there.
See [lifecycle states](/docs/api/nautilus/setAssetLifecycleState#states).

The lifecycle state written with the metadata is the one the NFT has on chain when `edit()`
reads it, unless the builder sets one with `setLifecycleState()`. The state an
`AssetBuilder` takes over from the fetched asset is not written back, so an edit built from a
copy fetched before a [`setAssetLifecycleState`](/docs/api/nautilus/setAssetLifecycleState)
(or one the index has not caught up with) does not undo that change.

To change a price without touching the DDO, use
[`setServicePrice`](/docs/api/nautilus/setServicePrice) instead.

## Returns

- Type: [`PublishResponse`](/docs/api/PublishResponse)

`services` contains only the services that were re-priced.

## Parameters

### asset

- Type: `NautilusAsset`

Built from an `AssetBuilder` constructed with a resolved asset.

### options (optional)

- Type: `PublishOptions`

Same as [`publish`](/docs/api/nautilus/publish#options-optional).

## Throws

- **Before any transaction:** an asset not built from a resolved DDO, `encrypt: false`, a
  `DEPRECATED` or `REVOKED_BY_PUBLISHER` state (requested or on chain), a missing
  `updateMetadata` or `deployERC20` permission, a missing or
  unsupported remote store, an invalid DDO, a DDO too large for the node to decrypt, an
  unreachable service endpoint or file, a failing store `check()`, or an
  `IndexerNonceStuckError` (see [`checkIndexerNonce`](/docs/api/nautilus/publish#checkindexernonce)).
- **After a datatoken was minted but before the metadata transaction:** a signed DDO too
  large for the node to decrypt (checked before it is stored), a failing `put()`, pointer
  validation or `verify()`, a failing pricing for a re-priced service, or a metadata
  transaction the wallet rejected or that was mined and reverted. The error is thrown as is,
  with `error.datatokens` listing the datatokens this call created. Once the envelope was
  stored it carries `error.stored` (type `StoredBeforeFailure`): the redacted pointer, the
  hash, and whether nautilus removed the unused object again (`cleanup: 'removed'`), could
  not (`'not-removed'`), or kept it because the metadata transaction had been sent and may be
  mined (`'kept'`), with the transaction's hash as `txHash` when it is known. A transaction
  the wallet sped up is not a failure: the replacement's receipt is the result. See [when a write fails](/docs/guides/remote-stores#when-a-write-fails-after-the-envelope-is-stored).
- **After the metadata transaction was mined:** a `MetadataConflictError`, or the
  `IndexingError` / `OceanNodeError` of `waitForIndexer`. Each carries the full
  `PublishResponse` as `error.published` (type `PublishedNotIndexed`) — see
  [`PublishResponse`](/docs/api/PublishResponse#when-the-write-was-mined-but-the-call-throws).
