# setAssetLifecycleState

Change an asset's lifecycle state on its NFT. The target is the asset, its DID or its NFT
address.

## Usage

```ts twoslash
import { LifecycleStates, Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
// ---cut---
// the NFT address you stored from the publish result
const nftAddress = '0x8d1f7c3B5bCb3D3E44a7F2bD2e1D0a4C5f6E7a8B'

const receipt = await nautilus.setAssetLifecycleState( // [!code focus]
  nftAddress, // [!code focus]
  LifecycleStates.REVOKED_BY_PUBLISHER // [!code focus]
) // [!code focus]
```

Resolves with the receipt once the transaction is **mined**, and throws if it was not
submitted or reverted. Within one instance, it waits for any `publish()`,
`completePublish()` or `edit()` of the same NFT still running before it sends its
transaction. It joins that queue when it is called, whatever the target: a DID is resolved
once its turn comes, so an `edit()` started after it, in the same tick or later, runs after
it.

**The current state is read from the chain**, not from a DDO: when the NFT is in the
requested state already, nothing is sent, it resolves `undefined` and logs
`lifecycle.state.unchanged`. An asset object fetched before someone else changed the state
does not decide this any more. After a change it logs the DID, the NFT address, the previous
state and the transaction hash: as `lifecycle.state.retired` (level `warn`, printed by
default) for `DEPRECATED` and `REVOKED_BY_PUBLISHER`, as `lifecycle.state.set` (level
`info`) for the other states.

### Which target to pass

| Target | Use it when | What is checked |
| --- | --- | --- |
| NFT address (`0x…`) | Always works, also once the node no longer serves the asset. Store it from the publish result. | A valid address; a mixed-case one must have a correct checksum. Nothing is resolved. |
| DID (`did:ope:…`) | The node still serves the asset. | The DDO the node serves must be the DID's ([`getAsset`](/docs/api/nautilus/getAsset)'s check), and its NFT must be the one the DID is derived from on the configured chain, so a wrong or malicious node cannot redirect an irreversible revoke to another NFT. When the node answers 404, the NFT named in its indexing record is used under the same check; ocean-node 4.2.2 records none for a deprecated or revoked asset, so the call then throws and asks for the NFT address. A DID that is not `did:ope:` (or `did:op:`) and 64 hex digits is refused before the node is asked. |
| Asset (`AssetV5`) | You have a fetched DDO at hand. | Its NFT must be the one its `id` is derived from, on the configured chain. Its lifecycle state is **not** used. |

For every target, before anything is sent, the NFT must have been created by the configured
ERC721 factory (checked first, before anything is read from the NFT itself), the signer must
hold the NFT's `updateMetadata` role (the publisher holds it by default; a manager can grant
it to others or remove it, the owner's too), and the NFT must carry metadata. Each refusal
ends in "Nothing was sent.", and so does a failed chain read, which says what could not be
read without the RPC's own error (that goes to the `rpc` debug topic, as it may carry the
RPC URL and its key). For `DEPRECATED` and `REVOKED_BY_PUBLISHER`, the errors after the
factory check and the `lifecycle.state.retired` message also name the NFT's ERC721 name and
symbol and its DID, so a wrong target is visible.

Revoking by DID alone once the node has dropped the asset (looking the NFT up in the chain's
logs instead) is not supported; it may come later as an opt-in. Until then, keep the NFT
address from the publish result.

To read the state back, use
[`getAssetLifecycleState`](/docs/api/nautilus/getAssetLifecycleState).

The states can also be set while editing, via
[`AssetBuilder.setLifecycleState`](/docs/api/assetbuilder/setLifecycleState) — use that when
you are changing metadata anyway, and this when the state is all you want to change.

## States

- Type: `LifecycleStates`

| Value | Name | Meaning |
| --- | --- | --- |
| `0` | `ACTIVE` | Normal. |
| `1` | `END_OF_LIFE` | Retired; no longer maintained. Reversible. ddo.js and ocean-node define it; ocean-node 4.2.2 serves the asset and decrypts its DDO, but refuses orders (only `ACTIVE` and `ASSET_UNLISTED` can be ordered). |
| `2` | `DEPRECATED` | Superseded by another asset. **One-way on ocean-node.** |
| `3` | `REVOKED_BY_PUBLISHER` | Withdrawn. **One-way on ocean-node.** |
| `4` | `ORDERING_DISABLED_TEMPORARILY` | Visible, but cannot be ordered. Reversible. |
| `5` | `ASSET_UNLISTED` | For markets to hide. The node still resolves it by DID and returns it in searches, flagged with the state. Reversible. |

:::warning[DEPRECATED and REVOKED are one-way]
Once an active asset moves to `DEPRECATED` or `REVOKED_BY_PUBLISHER`, it does not come back.
What the node serves afterwards depends on the node's version and database:

- **ocean-node 4.2.x with Elasticsearch drops the DDO.** The indexer deletes the full
  document, then fails to write the short one it means to keep, so
  [`getAsset`](/docs/api/nautilus/getAsset) answers 404 and the node's indexing state for the
  DID (`GET /api/aquarius/state/ddo?did=…`) records "Schema for version deprecated not found".
- **With Typesense, it keeps a short document** holding only the NFT state, without metadata
  or services.

The node drops or shortens the document only for a move **from `ACTIVE`**. From another state
(e.g. `ASSET_UNLISTED`), ocean-node 4.2.2 keeps serving the full DDO with
`indexedMetadata.nft.state` updated. Either way the state on chain is final.

Setting `ACTIVE` again does not restore it: only a new metadata write could, and
[`edit`](/docs/api/nautilus/edit) refuses an NFT in either state and needs the full published
DDO as its baseline, which the node no longer has. Treat both states as final. Assets cannot
be deleted; `REVOKED_BY_PUBLISHER` is the strongest state a publisher can set.

Revoking does not make the stored DDO unreadable either: the envelope stays in the remote
store, and a node that decrypts for anyone will still decrypt it. Remove it from the store
(`remove(stored.pointer)`) if it must go — see
[encrypted is not access control](/docs/guides/remote-stores#what-is-stored). Do that only for
an asset retired for good: without its creation envelope, a node reindex cannot restore it.
:::

`ASSET_UNLISTED` hides nothing by itself. The asset stays resolvable by DID and searchable on
the node, with `indexedMetadata.nft.state` set to `5`: a market must filter on that state to
leave it out.

### Reading the state

**Read the state from the chain, not from the node.** After a `DEPRECATED` or
`REVOKED_BY_PUBLISHER` change, a 4.2.x node with Elasticsearch has no document to read it
from. [`getAssetLifecycleState`](/docs/api/nautilus/getAssetLifecycleState) reads it from
the NFT, and takes the same targets. Pass the NFT address you stored from the publish
result; the DID works only while the node still serves the asset:

```ts twoslash
import { Nautilus, type NautilusAsset } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
declare const asset: NautilusAsset
// ---cut---
// at publish time: store the NFT address with your own records
const { nftAddress } = await nautilus.publish(asset)

// later, after the state change
const state = await nautilus.getAssetLifecycleState(nftAddress) // [!code focus]
```

A state change does not update the indexed transaction id either, so
[`waitForIndexer`](/docs/api/nautilus/waitForIndexer) with the receipt's hash cannot wait for
it. For the reversible states, polling [`getAsset`](/docs/api/nautilus/getAsset) and reading
[`getLifecycleState`](/docs/api/ddo/getLifecycleState) shows when the node has caught up.

DDO v5's `State` enum carries the same values and is accepted too. nautilus re-exports it as a
type only, so pass `LifecycleStates` members when you need a value.

## Returns

- Type: `TransactionReceipt | undefined`

The mined receipt. The standalone `setMetadataState({ nftAddress, state, chainConfig, signer })`
export behaves the same way and also waits for the receipt. A read straight after can still
show the old state on an RPC behind a load balancer whose nodes lag each other by a block.

## Parameters

### target

- Type: `LifecycleTarget` (`AssetV5 | string`)

The asset, its DID (`did:ope:…`; `did:op:` is accepted for the same hash) or its NFT address.
See [which target to pass](#which-target-to-pass).

### state

- Type: `LifecycleStates | State`

A number from `0` to `5`. The contract stores any `uint8` and ocean.js passes any number on,
but no other value has a meaning, so nautilus refuses it before anything is sent.

## Throws

- an `Error` ending in "Nothing was sent." when the state is not one of `LifecycleStates`,
  the target is not an asset, a well-formed DID or an address, the address checksum is
  wrong, the NFT is not the DID's or not the factory's, the signer lacks the metadata role,
  the NFT carries no metadata, or one of these could not be read from the chain ("…could not
  be read from the chain. Nothing was sent. Try again, or check the RPC.");
- an `Error` asking for the NFT address when the node does not serve the DID and its
  indexing record names no NFT (ocean-node 4.2.x after a deprecate or revoke), and one
  saying no asset is known for the DID when the node has no indexing record of it at all;
- the [`OceanNodeError`](/docs/api/node/OceanNodeClient) of a failed resolve, for a DID
  target;
- the transaction's error when it was not submitted or reverted.
