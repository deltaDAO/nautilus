# Editing

Editing an asset means republishing its metadata: fetch the published document, change what
you want, and write it back onto the same NFT.

## The pattern

```ts twoslash
import { AssetBuilder, IpfsRemoteStore, Nautilus } from '@deltadao/nautilus'
import { JsonRpcProvider, Wallet } from 'ethers'

const signer = new Wallet('0x...', new JsonRpcProvider('https://rpc.dev.pontus-x.eu'))
const config = { oceanNodeUri: 'https://ocean-node.dev.pontus-x.eu' }
const nautilus = await Nautilus.create(signer, {
  config,
  remoteStore: new IpfsRemoteStore({ uploadUrl: 'http://127.0.0.1:5001/api/v0/add' })
})
// ---cut---
// 1. Fetch what is published.
const current = await nautilus.getAsset('did:ope:2a6ebce0af...') // [!code focus]

// 2. Change only what you want.
const updated = new AssetBuilder(current) // [!code focus]
  .setName('A better name') // [!code focus]
  .build() // [!code focus]

// 3. Write it back.
const { ddo } = await nautilus.edit(updated) // [!code focus]
```

Editing needs a `remoteStore`, exactly as publishing does — the DDO is signed, encrypted
and stored off chain either way, in the same envelope format.

:::info
The merge is **structural**. Setting `name` leaves every other field of the published
document intact, so you never resupply metadata you are not changing. For contrast, the
ocean-cli does a shallow top-level merge, which for a v5 DDO means resupplying the entire
`credentialSubject` to change one field.
:::

The builder must be constructed **from a resolved asset**. That is what supplies the baseline
to merge over; passing a freshly built asset throws.

## What is stripped before signing

`datatokens`, `event` and `stats` are derived by the indexer from chain state, `proof` is the
signature the node attaches to every indexed DDO, and `accessDetails`, `views` and
`offchain` are decorations some clients attach to a resolved asset. All of them are removed before the document is signed, so a republish cannot bake in a
stale snapshot. You do not have to remember to delete them.

So are the JWT claims the previous signer added to the credential (`iss`, `sub`, `jti` and
the other registered claims): the edit's signature writes its own, so an edit signed by
another identity does not carry the previous signer's `iss`.

## Editing metadata

```ts twoslash
import { AssetBuilder, Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const published = await nautilus.getAsset('did:ope:2a6ebce0af...')
// ---cut---
const metadataEdit = new AssetBuilder(published)
  .setName('Hourly Weather Observations, 2020–2026')
  .setDescription('Now covering six years')
  .addTags(['revised'])
  .setLicense({ name: 'CC-BY-4.0' }) // [!code focus]
  .build()
```

`created` is preserved and `updated` is bumped for you.

## Editing a service

Load the published service with the [`ServiceBuilder`](/docs/api/ServiceBuilder), change it,
and add it back:

```ts twoslash
import {
  AssetBuilder,
  FileTypes,
  Nautilus,
  ServiceBuilder,
  ServiceTypes,
  getServices
} from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const published = await nautilus.getAsset('did:ope:2a6ebce0af...')
// ---cut---
const serviceId = getServices(published)[0].id

const revisedService = new ServiceBuilder<ServiceTypes.ACCESS, FileTypes.URL>({
  asset: published, // [!code focus]
  serviceId // [!code focus]
})
  .setName('Access Service, revised')
  .setTimeout(7200)
  .build()

const serviceEdit = new AssetBuilder(published).addService(revisedService).build()
```

Services are matched by id, so this replaces the published one rather than adding a second.

### Changing files changes the service id

A service's id is the hash of its encrypted file object. Replace the files — or the endpoint,
since a different node must re-encrypt them — and the rebuilt service necessarily gets a new
id. nautilus removes the old entry so the two do not linger side by side.

```ts twoslash
import {
  AssetBuilder,
  FileTypes,
  Nautilus,
  ServiceBuilder,
  ServiceTypes,
  getServices
} from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const published = await nautilus.getAsset('did:ope:2a6ebce0af...')
// ---cut---
const newFiles = new ServiceBuilder<ServiceTypes.ACCESS, FileTypes.URL>({
  asset: published,
  serviceId: getServices(published)[0].id
})
  .addFile({ // [!code focus]
    type: 'url', // [!code focus]
    url: 'https://data.example/observations-v2.csv', // [!code focus]
    method: 'GET' // [!code focus]
  }) // [!code focus]
  .build()
```

Consumers holding an order against the old service id keep it, but new orders go to the new
one.

The endpoint cannot change on its own: the files are encrypted for the node in the service's
endpoint, so a loaded service whose `setServiceEndpoint` changed but which has no files added
again fails with *"Cannot encrypt files: no files were added to this service. Its
serviceEndpoint changed, …"*. Add the files again with `addFile()` in the same edit.

## Adding and removing services

```ts twoslash
import {
  AssetBuilder,
  FileTypes,
  Nautilus,
  ServiceBuilder,
  ServiceTypes,
  getServices
} from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const published = await nautilus.getAsset('did:ope:2a6ebce0af...')
// ---cut---
const extraService = new ServiceBuilder<ServiceTypes.COMPUTE, FileTypes.URL>({
  serviceType: ServiceTypes.COMPUTE
})
  .setServiceEndpoint('https://ocean-node.dev.pontus-x.eu')
  .setName('Compute')
  .addFile({ type: 'url', url: 'https://data.example/x.csv', method: 'GET' })
  .setPricing({ type: 'free' }) // a new service needs its own datatoken
  .build()

const withExtra = new AssetBuilder(published)
  .addService(extraService) // [!code focus]
  .removeService(getServices(published)[0].id) // [!code focus]
  .build()
```

Only services carrying a **new pricing config** get a new datatoken. That is why
`setPricing` is required on a genuinely new service and blocked on a loaded one.

## What an edit cannot change

An `AssetBuilder` constructed from a resolved asset is an **edit builder**, and a
`ServiceBuilder` constructed with `{ asset, serviceId }` edits a published service. They
refuse, with an error, the setters an edit cannot apply. Earlier releases accepted them and
ignored them silently:

| Setter | On an edit | Why |
|---|---|---|
| `setType()` | throws | A published asset keeps its type; its services were built for it. Publish a new asset to change it. |
| `setNftData()`, `setNftTokenName()`, `setNftTokenSymbol()`, `setNftTokenUri()`, `setNftTokenTransferable()`, `setNftTokenTemplate()` | throw | The NFT exists already, and an edit does not change it. |
| `setDatatokenData()`, `setDatatokenNameAndSymbol()` on a loaded service | throw | The service's datatoken exists already. |
| `setPricing()` on a loaded service | throws | A new datatoken would change the service id; use [`setServicePrice()`](#changing-a-price). |

The datatoken setters stay valid on a **new** service that an edit adds: `edit()` creates its
datatoken with them.

### Who gets the new datatokens

A new service added by an edit gets a new datatoken. Its minter and payment collector (who
can mint it freely, and who collects its payments when it is priced) is the **NFT's owner as
your RPC reports it** (`ownerOf`), also when a manager-role account signs the edit. That
owner needs the `deployERC20` permission on the NFT, which the NFT gives its owner; when it
lacks it, `edit()` throws before any transaction and names
[`setOwner(<signer>)`](/docs/api/assetbuilder/setOwner) as the way out.

The owner named in the resolved DDO is never used. ocean-node reports there the account that
wrote the metadata last, not the NFT's owner: after a manager's edit it names the manager,
after an NFT transfer it still names the old owner until the next edit, and a malicious node
can name anyone. [`setOwner()`](/docs/api/assetbuilder/setOwner) may name only the signer or
the on-chain owner; any other address makes `edit()` throw before any transaction. Naming
the signer when it is not the owner logs a visible warning (`edit.owner.not_nft_owner`): its
payments then go to the signer.

The NFT whose owner is read is tied to the DID you resolved, so a node cannot point an edit
at another NFT. [`getAsset()`](/docs/api/nautilus/getAsset),
[`getAssets()`](/docs/api/nautilus/getAssets) and
[`waitForIndexer()`](/docs/api/nautilus/waitForIndexer) refuse a DDO whose id is not the
DID asked for, and `edit()` refuses, before any transaction, a DDO whose id is not the DID
of its `nftAddress` on the configured chain. [`query()`](/docs/api/nautilus/query) results
are not checked against any DID: `edit()` still ties such a DDO's NFT to its own id, but
check that the id is the DID you mean to edit.

```ts twoslash
import {
  AssetBuilder,
  FileTypes,
  Nautilus,
  ServiceBuilder,
  ServiceTypes
} from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const published = await nautilus.getAsset('did:ope:2a6ebce0af...')
const managerAddress = '0x0DB823218e337a6817e6D7740eb17635DEAdafAF'
const extraService = new ServiceBuilder<ServiceTypes.ACCESS, FileTypes.URL>({
  serviceType: ServiceTypes.ACCESS
})
  .setServiceEndpoint('https://ocean-node.dev.pontus-x.eu')
  .addFile({ type: 'url', url: 'https://data.example/x.csv', method: 'GET' })
  .setPricing({ type: 'free' })
  .build()
// ---cut---
// Signed by a manager: the new datatoken goes to the NFT's owner on chain.
const edit = new AssetBuilder(published).addService(extraService)

// Or to the manager itself, with a warning. Any third address throws.
edit.setOwner(managerAddress) // [!code focus]
```

### Who signs: the issuer

The edit builder starts with the issuer of the published asset, and the edit must be signed
by that identity. To re-issue the asset under another one — a manager-role account, or the
new owner after an NFT transfer — call [`setIssuer()`](/docs/api/assetbuilder/setIssuer) with
the identity that signs the edit. Otherwise `edit()` throws `The DDO declares issuer "…" but
it is being signed by "…"` before any transaction, so no datatoken is created for nothing.

## Changing a price

Do not do it through the builder — a new pricing config mints a new datatoken and changes the
service id. There is a dedicated call that just sets the rate on the existing exchange:

```ts twoslash
import { Nautilus, getServices } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const published = await nautilus.getAsset('did:ope:2a6ebce0af...')
// ---cut---
await nautilus.setServicePrice(published, getServices(published)[0].id, '2.5') // [!code focus]
```

Only works for fixed-rate services: a free service has a dispenser, which has no rate.

## Editing compute options

```ts twoslash
import {
  AssetBuilder,
  FileTypes,
  Nautilus,
  ServiceBuilder,
  ServiceTypes,
  getServiceByType
} from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const computeAsset = await nautilus.getAsset('did:ope:2a6ebce0af...')
// ---cut---
const computeServiceId = getServiceByType(computeAsset, 'compute')?.id as string

const revisedCompute = new ServiceBuilder<ServiceTypes.COMPUTE, FileTypes.URL>({
  asset: computeAsset,
  serviceId: computeServiceId
})
  .allowAlgorithmNetworkAccess(false)
  .addTrustedAlgorithms([{ did: 'did:ope:926098d069b017dcf...' }]) // [!code focus]
  .removeTrustedAlgorithmPublisher('0x0DB823218e337a...')
  .build()

const computeEdit = new AssetBuilder(computeAsset).addService(revisedCompute).build()
```

Trusted algorithms are re-resolved to their current container and file checksums on every
edit, so an algorithm whose container moved gets its pin updated.

## Changing the lifecycle state

To retire or unlist an asset without touching anything else, one transaction is enough.
Pass the asset, its DID or its NFT address; the NFT address keeps working once the node no
longer serves the asset:

```ts twoslash
import { LifecycleStates, Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const nftAddress = '0x8d1f7c3B5bCb3D3E44a7F2bD2e1D0a4C5f6E7a8B'
// ---cut---
await nautilus.setAssetLifecycleState(nftAddress, LifecycleStates.ASSET_UNLISTED) // [!code focus]
```

It resolves once the transaction is mined, and returns `undefined` without sending anything
when the NFT is already in that state **on chain** (a fetched asset's own state is not
used). A DID is bound to its NFT before anything is sent, so a wrong or malicious node cannot
redirect a revoke; see [which target to pass](/docs/api/nautilus/setAssetLifecycleState#which-target-to-pass).
If you are changing metadata anyway, set it on the builder instead with
[`setLifecycleState`](/docs/api/assetbuilder/setLifecycleState).

Without `setLifecycleState`, `edit()` writes the state the NFT has on chain at that moment,
not the one in the asset you built from. So an edit built from a copy you fetched before
unlisting the asset keeps it unlisted.

:::warning[DEPRECATED and REVOKED are one-way]
Moving an active asset to `DEPRECATED` (2) or `REVOKED_BY_PUBLISHER` (3) cannot be undone.
What the node serves afterwards depends on the node's version and database: **ocean-node
4.2.x with Elasticsearch drops the DDO**, so `getAsset` answers 404; with Typesense it keeps a
short document holding only the NFT state.
Setting `ACTIVE` again does not bring it back, and the node will not decrypt or index new
metadata for it either, so `edit()` refuses such an asset before spending anything. Use `END_OF_LIFE` (1), `ORDERING_DISABLED_TEMPORARILY` (4) or `ASSET_UNLISTED` (5)
for anything you may want to undo.

Assets cannot be deleted. `REVOKED_BY_PUBLISHER` is the strongest state a publisher can set,
which makes it the way to retire test assets for good.
:::

`ASSET_UNLISTED` does not hide an asset by itself: the node still resolves it by DID and
returns it in searches, with `indexedMetadata.nft.state` set to `5`. Markets must filter on
that state.

A lifecycle change does not update the indexed transaction id, so
`waitForIndexer(did, receipt.hash)` cannot wait for it. Read the state from the chain instead,
with [`getAssetLifecycleState`](/docs/api/nautilus/getAssetLifecycleState) and the NFT
address: after a `DEPRECATED` or `REVOKED_BY_PUBLISHER` change, a 4.2.x node has no document
to read it from, and `getAsset` answers 404 with a hint saying so.

## Waiting for the change to be visible

The metadata transaction confirms before ocean-node has indexed it, so an immediate re-read
can still return the old document. Wait for your specific transaction:

```ts twoslash
import { AssetBuilder, Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const published = await nautilus.getAsset('did:ope:2a6ebce0af...')
// ---cut---
const { ddo, setMetadataTxReceipt } = await nautilus.edit(
  new AssetBuilder(published).setName('Renamed').build()
)

const indexed = await nautilus.waitForIndexer( // [!code focus]
  ddo.id as string, // [!code focus]
  setMetadataTxReceipt.hash // [!code focus]
) // [!code focus]
```

Passing the transaction hash matters here: without it, `waitForIndexer` is satisfied by the
asset merely existing, which it already did. If the node rejects the update, the wait throws
an `IndexingError` with the node's message rather than timing out.

## One metadata event per block

ocean-node indexes only the **first** `MetadataCreated` or `MetadataUpdated` event of an asset
in a block and ignores the rest, and nothing on chain shows that it dropped one.

Within one `Nautilus` instance this cannot happen. Its `publish()` (once the NFT is minted),
`completePublish()`, `edit()` and `setAssetLifecycleState()` calls for one NFT run one after
the other, and each waits for its receipt before the next one sends anything. `edit()` reads
the NFT's lifecycle state and checks the signer's permissions only once its turn comes, so it
sees a revoke this instance started before it. It does **not** wait for the previous change
to be indexed; pass `waitForIndexer` (or call
[`waitForIndexer`](/docs/api/nautilus/waitForIndexer)) when you need to read it back.

Separate instances or processes writing to the same asset can still land in one block. So
after every metadata transaction, nautilus reads that block's logs, and if it finds another
metadata event for the same NFT it throws a `MetadataConflictError`:

```ts twoslash
import { MetadataConflictError, Nautilus, type NautilusAsset } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
declare const edited: NautilusAsset
// ---cut---
try {
  await nautilus.edit(edited)
} catch (error) {
  if (!(error instanceof MetadataConflictError)) throw error

  error.published // the full PublishResponse: the transaction was mined // [!code focus]
  error.conflictingTxIds // the other metadata transactions in that block // [!code focus]
  error.indexedFirst // whether this one came first, so it is the one the node keeps // [!code focus]
}
```

Write the metadata again with `edit()` to bring the chain and the index back in line. The
check is best effort: when the logs cannot be read, nautilus logs a warning and returns
normally.

## Try it

Each edit on this page is a command in [`examples/`](/docs/examples):

```sh
npm start -- edit:metadata did:ope:… "New name"
npm start -- edit:service did:ope:… first "New service name"      # keeps the service id
npm start -- edit:service-files did:ope:… first https://…/v2.csv   # gives a new service id
npm start -- edit:service-allow did:ope:… first 0x… 0x…            # service-level allowlist
npm start -- edit:price did:ope:… 2.95
npm start -- edit:trusted-algorithms <datasetDid> <algoDid> [...]
npm start -- asset:unlist did:ope:…      # flag it unlisted for markets (reversible)
```
