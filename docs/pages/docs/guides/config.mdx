# Custom Configuration

nautilus resolves the chain from your signer's provider and then merges ocean.js's default
config for that chain with whatever you pass in `config`.

```ts twoslash
import { JsonRpcProvider, Wallet } from 'ethers'
import { Nautilus } from '@deltadao/nautilus'

const signer = new Wallet('0x1234', new JsonRpcProvider('https://rpc.dev.pontus-x.eu'))

const nautilus = await Nautilus.create(signer, {
  config: { // [!code focus]
    oceanNodeUri: 'https://ocean-node.dev.pontus-x.eu' // [!code focus]
  } // [!code focus]
})
```

:::warning
In v1 the config was the second argument directly. It now lives under a `config` key,
because `Nautilus.create` also takes a remote store, a DDO signer and a credential
provider. See [`create`](/docs/api/nautilus/create).
:::

## What changed from v1

The `Config` type moved with the stack. Three fields nautilus v1 relied on are gone:

| v1 field | v2 |
| --- | --- |
| `metadataCacheUri` | **`oceanNodeUri`** — one node serves metadata, provider services and the indexer |
| `providerUri` | **`oceanNodeUri`** — same node |
| `subgraphUri` | **removed** — pricing is derived from chain reads and the DDO's indexed stats |

New fields worth knowing about: `escrow` (compute payments), `accessListFactory`
(access-list gating), and `sdk`, which is `'oasis'` on confidential EVMs and `'evm'`
elsewhere.

## The ocean-node URI

The single most important setting. One ocean-node replaces the old Aquarius plus Provider
pair, so this is where metadata resolution, file encryption, download URLs and compute all
go:

```ts twoslash
import type { Config } from '@oceanprotocol/lib'
// ---cut---
const customConfig: Partial<Config> = {
  oceanNodeUri: 'https://ocean-node.dev.pontus-x.eu' // [!code focus]
}
```

A peer id or multiaddr also works instead of an HTTP URL, in which case ocean.js talks to
the node over libp2p rather than REST.

An HTTP URL must be `https://`, except on `localhost`, `127.0.0.0/8`, `::1` and `*.localhost`:
the plaintext DDO pointer and the signed DDO go to this node for encryption, and node auth
travels with every request. `Nautilus.create` throws for a plain `http://` URI elsewhere
unless you pass `allowInsecureTransport: true` next to `config`.

The URL is judged the way `fetch` parses it, so spellings such as `http:host` or `http:/host`
count as plain `http://`, and a URL containing a tab, a line break or another control
character is refused. `*.localhost` names are trusted without being resolved; they are
reserved for loopback (RFC 6761), but if your resolver does not map them there, use
`localhost` or `127.0.0.1` instead.

It must be an
[OceanProtocolEnterprise ocean-node](https://github.com/OceanProtocolEnterprise/ocean-node)
4.2.x — see [which node](/docs/guides/ocean-node#which-node). For access to the deltaDAO test
environment, or to have your own ocean-node run as a service, contact deltaDAO at
[delta-dao.com/contact](https://delta-dao.com/contact) or
[contact@delta-dao.com](mailto:contact@delta-dao.com).

The same node encrypts your DDO and its pointer, and its URI is written on chain as the
node that can decrypt them, so keep publishing and editing an asset through the same node.

## The RPC endpoint

`nodeUri` is the **blockchain** RPC, not the ocean-node — an easy pair to confuse. In
practice you rarely set it, because nautilus uses the provider already attached to your
signer for every transaction.

```ts twoslash
import type { Config } from '@oceanprotocol/lib'
// ---cut---
const customConfig: Partial<Config> = {
  nodeUri: 'https://rpc.dev.pontus-x.eu' // [!code focus]
}
```

## Concurrency and nonces

Every transaction nautilus sends goes through a **nonce guard** that `Nautilus.create` wraps
around your signer. It exists because ocean.js swallows a failed send and returns `null`,
and because each send used to read its nonce from the RPC on its own: two publishes, a
publish and an order, or two orders of one key running at once could read the same nonce,
and one of them failed with only "ocean.js returned no transaction"; so did a send after a
stale nonce read from the RPC.

With the default `nonceManagement: 'auto'` and a signer that signs locally (an ethers
`Wallet`):

- **One send at a time per chain and address**, in this process: building the transaction
  and broadcasting it are serialised, waiting for it to be mined is not. Concurrent calls
  of one instance, and of several instances with the same key, get consecutive nonces.
- **The nonce is `max(nautilus's counter, the RPC's pending count)`**: a pending count the
  RPC answers from stale state is masked once nautilus has sent with the key. The counter
  advances only after a successful broadcast, so a refused send leaves no gap; if the RPC
  forgets a transaction nautilus counted (dropped from its pool), the counter falls back to
  the pending count (`chain.nonce.counter_reset`).
- **Recovery from nonce refusals only** (`NONCE_EXPIRED` / "nonce too low",
  `REPLACEMENT_UNDERPRICED`, "already known"), and only for a refused transaction that is
  provably this send's (same sender, recipient and data):
  - the chain already has it by hash: nautilus waits for that one and **never sends it
    again** (`chain.nonce.already_sent`);
  - it does not: the same transaction is sent again with a fresh nonce, the next one the
    RPC names, else the highest of the counter, `pending` and `latest`; at most three
    attempts, 0.5 to 2 seconds apart (`chain.nonce.resending`);
  - an **order, purchase, approval or escrow payment** (any call not known to move no
    value) is sent again only with proof the first one can never be mined: its hash unknown
    on two reads (the second through `verificationProvider` when you set one) and the
    account's mined count past its nonce. Otherwise nautilus stops with a `NonceGuardError`
    whose `reason` is `'may-have-been-sent'`: check the account's transactions before
    retrying.
- **Never a retry** after a timeout, a network error or any other refusal: the transaction
  may have landed.
- **The cause is named.** When ocean.js returns no transaction, the error says why
  (`startOrder failed: …REPLACEMENT_UNDERPRICED…`), with the guard's error or the RPC's
  refusal as `cause`. No error message carries a signed transaction: an unmined signed
  transaction can be broadcast by anyone who reads it.

```ts twoslash
import { JsonRpcProvider, Wallet } from 'ethers'
import { Nautilus, NonceGuardError, type NautilusAsset } from '@deltadao/nautilus'
const signer = new Wallet('0x1234', new JsonRpcProvider('https://rpc.dev.pontus-x.eu'))
declare const assets: NautilusAsset[]
// ---cut---
const nautilus = await Nautilus.create(signer, {
  nonceManagement: 'auto', // the default // [!code focus]
  verificationProvider: new JsonRpcProvider('https://rpc2.example.org') // [!code focus]
})

// Safe from one key in one process: nonces come out consecutive.
const results = await Promise.allSettled(assets.map((asset) => nautilus.publish(asset)))

for (const result of results)
  if (
    result.status === 'rejected' &&
    result.reason?.cause instanceof NonceGuardError &&
    result.reason.cause.reason === 'may-have-been-sent'
  )
    console.warn('check the account before retrying:', result.reason.cause.attempts)
```

**Wallet-managed signers** (`JsonRpcSigner`, a browser wallet through `BrowserProvider`)
assign nonces themselves: nautilus sets none and sends nothing again, but still returns a
refused transaction the chain already has and names the cause of a failed send. So does
`nonceManagement: 'off'`, for any signer.

:::warning[One key per process]
The guard serialises sends in **this process** only. Two processes (two servers, a server
and a script, two CI jobs) that send with the same key can still collide; the recovery
covers the occasional collision, but an order that collides and cannot be proven unsent
stops with "may have been sent". Give each process its own key, or send through one
process.
:::

### `NonceGuardError`

What the guard throws when it stops after a nonce refusal. On the ocean.js path (an order,
a datatoken, pricing) it is the `cause` of the operation's error; for the metadata
transaction it is the error itself (inside a `PublishIncompleteError` on publish).

| Field | Meaning |
| --- | --- |
| `reason` | `'may-have-been-sent'`: not provably unsent, it may still be mined; `'attempts-exhausted'`: refused three times; `'unverifiable'`: the refusal carries no signed transaction of this send; `'not-managed'`: the nonce was set by the caller, by the wallet, or `nonceManagement` is `'off'` |
| `code` | the ethers code of the last refusal, e.g. `NONCE_EXPIRED` |
| `attempts` | `{ hash, nonce }` of each refused signed transaction, to look up before retrying |
| `moneySend` | whether the transaction moves value |

To see the guard's decisions, set `NAUTILUS_DEBUG=sensitive` (optionally
`NAUTILUS_DEBUG_TOPICS=nonce`): it prints the nonce reads, the signed transactions of
refused sends and each recovery decision. Signed transactions are sensitive, see
[Debugging](/docs/guides/debugging). The `chain.nonce.*` warnings print at the default log
level.

## An unsupported network

ocean.js's `ConfigHelper` ships defaults for a set of chains, among them
**Pontus-X devnet (32456)** and **OP Sepolia (11155420)**. Check
`nautilus.getOceanConfig()` to see what you got. On a chain it does not know, supply the
addresses yourself.

`Nautilus.create` validates `nftFactoryAddress`, `fixedRateExchangeAddress` and
`dispenserAddress` up front, so a missing one fails immediately with a message naming it —
rather than halfway through a publish.

`chainId` cannot select another network: the chain always comes from the signer's provider,
and a `config.chainId` that differs from it throws. Connect the signer to the RPC of the
chain you want.

```ts twoslash
import type { Config } from '@oceanprotocol/lib'
// ---cut---
const customConfig = {
  chainId: 32456,
  network: 'pontusx',

  // The ocean-node: metadata, provider services and the indexer.
  oceanNodeUri: 'https://ocean-node.dev.pontus-x.eu',
  // The blockchain RPC.
  nodeUri: 'https://rpc.dev.pontus-x.eu',

  // Validated at construction.
  nftFactoryAddress: '0xFdC4a5DEaCDfc6D82F66e894539461a269900E13',
  fixedRateExchangeAddress: '0x8372715D834d286c9aECE1AcD51Da5755B32D505',
  dispenserAddress: '0x5461b629E01f72E0A468931A36e039Eea394f9eA',

  oceanTokenAddress: '0xdF171F74a8d3f4e2A789A566Dce9Fa4945196112',
  oceanTokenSymbol: 'OCEAN',
  providerAddress: '0x68C24FA5b2319C81b34f248d1f928601D2E5246B'
} satisfies Partial<Config>
```

For paid compute, set `escrow` to the chain's **EnterpriseEscrow** contract, which is where
paid jobs lock their funds. Pontus-X devnet's address data in ocean.js lists no escrow, so
paid compute is refused there until you set it. On a chain whose address data has one,
leave `escrow` out: nautilus funds the chain's `EnterpriseEscrow` (else its `Escrow`). See
[Escrow contract](/docs/api/nautilus/compute#escrow-contract).

For the full set of fields, see the
[ocean.js `Config`](https://github.com/oceanprotocol/ocean.js/blob/main/src/config/Config.ts).

## Reading back the resolved config

Useful for checking what the defaults actually gave you:

```ts twoslash
import { Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
// ---cut---
const config = nautilus.getOceanConfig() // [!code focus]
```
