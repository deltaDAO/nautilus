# Ocean Node client [The escape hatch under every nautilus call]

In v1 there were two services: Aquarius for metadata and Provider for everything else. v2
talks to a single **ocean-node**, which serves metadata, provider services, the indexer and
compute — which is why `metadataCacheUri` and `providerUri` collapsed into one
`oceanNodeUri`.

Most of the time nautilus wraps this for you. When it does not, take the client.

```ts twoslash
import { Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
// ---cut---
const node = nautilus.getNodeClient() // [!code focus]

const status = await node.getNodeStatus()
```

## Which node

nautilus 2.0.0-beta.1 works with
[OceanProtocolEnterprise ocean-node](https://github.com/OceanProtocolEnterprise/ocean-node)
**4.2.x**, unmodified. Upstream `oceanprotocol/ocean-node` 4.0 and 4.2 cannot resolve remote
DDOs, so assets published to them are never indexed.

With an IPFS remote store, the node also needs an IPFS gateway (`IPFS_GATEWAY`) that can
fetch your store's content — see [remote stores](/docs/guides/remote-stores#storage-options).

Do not publish with the node's own key. The indexer signs its decrypt calls with the node's
key (`providerAddress`), so with the same key as publisher their nonces collide, decrypt fails
with 401, and the asset goes on chain without ever being indexed. `publish`,
`completePublish` and `edit` warn once when they see it;
[`getNodeAddress()`](/docs/api/node/OceanNodeClient#getnodeaddress) returns the address.

:::warning[A node can stop indexing on its own]
ocean-node 4.2 has faults that can stop a node from indexing or make orders revert, whoever
publishes. See [known ocean-node 4.2 issues](#known-ocean-node-42-issues) for what they are
and what nautilus does about each.
:::

:::tip
For access to the deltaDAO test environment, or to have your own ocean-node run as a
service, contact deltaDAO at [delta-dao.com/contact](https://delta-dao.com/contact) or
[contact@delta-dao.com](mailto:contact@delta-dao.com).
:::

## Known ocean-node 4.2 issues

These are bugs or limits in ocean-node 4.2.x (Enterprise), not in nautilus. They hit any
client. nautilus avoids, detects or reports what it can.

| Issue | Effect | What nautilus does |
| --- | --- | --- |
| **Stuck indexer nonce** (B1) | The indexer signs its decrypt calls over the 32-byte hash, the node verifies them with leading zero bytes stripped. At the first nonce whose hash starts with `0x00` (about 1 in 256) the node refuses its own call (`401 … signature mismatch`), the stored nonce never advances, and nothing encrypted is indexed again. A restart does not help. | `publish`, `completePublish` and `edit` read [`getIndexerNonceState()`](/docs/api/node/OceanNodeClient#getindexernoncestate) before the first transaction and throw an `IndexerNonceStuckError` when `stuck` (opt out with `checkIndexerNonce: false`; a node that does not answer is skipped). They warn when this publish's own second decrypt would hit the bad nonce. An `IndexingError` for the 401 names the cause. |
| **Mis-signed provider fees** (B2) | The node signs fees the same wrong way, so about 1 in 256 `startOrder`/`reuseOrder` calls revert on chain (`Invalid provider fee`). | Before any approval or order, nautilus recovers the fee's signer exactly as the datatoken does. On a mismatch it asks the node for a new fee (up to 3 times, a second apart), then throws a `ProviderFeeSignatureError` with nothing spent. Compute fees, and download fees of a service with `timeout: 0`, come out the same every time on 4.2, so such a fee cannot be refreshed: the order is refused until the node is fixed. |
| **100 KB decrypt body limit** | The node parses every JSON request with express's default 100 KB limit, including its own decrypt call that carries the envelope back. A signed DDO over about 24 000 characters of JWS (roughly 18 KB of DDO JSON) gets a `413` and is never indexed. | `publish`, `completePublish` and `edit` refuse such a DDO before the first transaction (from the DDO) and again before storing it (from the real ciphertext), with a 4 KB margin. |
| **The node rate-limits itself** | The indexer calls the node's own public URL, so `MAX_REQ_PER_MINUTE` (default 30 per IP) and `MAX_CONNECTIONS_PER_MINUTE` (default 120 IPs) apply to it. A burst of publishes, or a reindex, gets `429`/`403` and those events fail for good. | Nothing it can prevent; publish in small batches. Its own [`waitForIndexer`](/docs/api/nautilus/waitForIndexer#polling-rate-and-rate-limits) polls at most 18 times a minute and backs off on `429`/`403`. Operators should raise the limits. |
| **Failed events are not retried** | Any failure while indexing `MetadataCreated` (a gateway timeout, a 5xx, any of the above) is final, and later `MetadataUpdated` events of an asset with no stored DDO are ignored. Only an admin `reindexTx` repairs it. A reindex needs the creation envelope again. | It reads the stored envelope back before the metadata transaction (`RemoteStore.verify`). Keep the creation envelope of every live asset: see [cleaning up](/docs/guides/remote-stores#cleaning-up). |
| **UNLISTED / END_OF_LIFE ordering** (4.2.0) | The ordering check tests array indices instead of values: `ASSET_UNLISTED` (5) assets cannot be ordered, `END_OF_LIFE` (1) assets can. | Nothing. Fixed in 4.2.1. |
| **C2D engine stall** (seen in local tests, unconfirmed) | In local runs on 4.2.0 the Docker compute engine sometimes stopped processing jobs after a job was stopped right after it was created. The stuck jobs kept their CPU, so later jobs failed with `Not enough available cpu in this environment` until the node restarted. Not reproduced on purpose, not seen elsewhere. | Nothing. |

The first two are signature-encoding bugs in the node. A node-side fix exists but is not in
any published 4.2 release; until a node runs it, the operator can unstick a stuck indexer by
advancing the stored nonce of the node's own address once, with any command signed with the
node key the way ocean.js signs.

## Checking what you are pointed at

Worth doing first when something behaves unexpectedly — a v1 Provider and an ocean-node
answer on the same port but are not the same thing.

```ts twoslash
import { Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
// ---cut---
const node = nautilus.getNodeClient()

const ok = await node.isValidNode() // [!code focus]
const status = await node.getNodeStatus() // [!code focus]
```

## Authentication

The client accepts three forms of auth, expressed as `NodeAuth`:

| Form | When |
| --- | --- |
| `Signer` | The default. Each call does a nonce-and-sign round trip. |
| JWT auth token | Skips that round trip. **Requires `consumerAddress`**, because nautilus cannot decode the token. |
| Pre-computed signature | You already hold `{ consumerAddress, signature, nonce }`. |

Minting a token is worth it for anything doing many calls:

```ts twoslash
import { createAuthToken, revokeAuthToken } from '@deltadao/nautilus'
import { Wallet } from 'ethers'

declare const signer: Wallet
const nodeUri = 'https://ocean-node.dev.pontus-x.eu'
// ---cut---
const token = await createAuthToken(signer, nodeUri) // [!code focus]

// … many calls later
await revokeAuthToken(signer, token, nodeUri) // [!code focus]
```

:::warning
`resolveConsumerAddress` throws for a JWT with no `consumerAddress` supplied — ocean.js does
not re-export the `decodeJwt` helper that would let nautilus read it out of the token. Pass
the address explicitly whenever you authenticate with a token.
:::

## Calls nautilus does not wrap

### Files

```ts twoslash
import { Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const node = nautilus.getNodeClient()
// ---cut---
// What the node can see about a file, before you publish it.
const info = await node.getFileInfo(
  { type: 'url', url: 'https://data.example/x.csv', method: 'GET' } as never
)

// Whether a published asset's files are still readable.
const check = await node.checkDidFiles('did:ope:1234abcd...', 'service-id') // [!code focus]
```

`checkDidFiles` is the quickest way to find out whether an asset has rotted — a file server
that went away shows up here rather than at download time.

### Buckets

The node's persistent storage, which is what
[`NodePersistentRemoteStore`](/docs/api/remote/NodePersistentRemoteStore) uses underneath.
Buckets work for asset files (`nodePersistentStorage` file objects), but **not for DDOs**:
ocean-node 4.2 resolves a remote DDO without a consumer address, and a bucket refuses that
read.

```ts twoslash
import { Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const node = nautilus.getNodeClient()
// ---cut---
const bucketId = await node.createBucket([], 'my-bucket') // [!code focus]

// `content` is a request body stream, not a string — a web `ReadableStream`,
// a Node stream or a `Blob` all work.
await node.uploadFile(bucketId, 'notes.txt', new Blob(['hello']).stream()) // [!code focus]

const object = await node.getFileObject(bucketId, 'notes.txt')
```

### Indexing state

When an asset is on chain but `getAsset` says "DDO not found", the node has usually recorded
why. Its indexing state is the only place that shows it — nothing appears on chain, and the
node does not retry a failed event.

```ts twoslash
import { Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const node = nautilus.getNodeClient()
declare const did: string
declare const txHash: string
// ---cut---
const failure = await node.getIndexingState({ txId: txHash }) // [!code focus]
// e.g. { did: 'did:op:…', nft: '0x…', txId: '0x…', valid: false, error: 'Provider exception on decrypt DDO. …' }

const success = await node.getIndexingState({ did }) // [!code focus]
// e.g. { did: 'did:ope:…', txId: ' ', valid: true, error: ' ' }
```

This is `GET <node>/api/aquarius/state/ddo?txId=<hash>` (or `?did=<did:ope:…>`, or
`?nft=<address>`), so `curl` works too — but the node matches the values exactly, as it filed
them: `nft` checksummed, `txId` lower-case. `getIndexingState` normalizes both for you and
rejects a malformed `nft`, `txId` or `did`. The node keeps two kinds of record under
different ids:

- **Success** records are filed under the asset's `did:ope:` DID, with no `nft` and a blank
  `txId` (`" "`). Find them with `?did=did:ope:…`.
- **Failure** records are filed under the old `did:op:` form of the id, with `nft` and the
  real `txId`. Find them with `?txId=` (preferred) or `?nft=`.
- **Failure records are never removed.** After a later successful edit, `?nft=` can still
  return the old error. Check that the record's `txId` is the transaction you care about.

Treat `valid: false` **or** any non-blank `error` as a failure — a DDO dropped by schema
validation is recorded as `valid: true` plus an error.

[`waitForIndexer`](/docs/api/nautilus/waitForIndexer) reads the record for its transaction
for you, and throws an `IndexingError` with the node's message. See
[how the node resolves your DDO](/docs/guides/remote-stores#how-the-node-resolves-your-ddo)
for what it checks.

### Remote validation

[Local validation](/docs/guides/validation) is what `publish` runs. If you also want the
node's opinion:

```ts twoslash
import { Nautilus } from '@deltadao/nautilus'
import { Wallet } from 'ethers'
const nautilus = await Nautilus.create(new Wallet('0x1234'))
const node = nautilus.getNodeClient()
declare const ddo: Record<string, unknown>
// ---cut---
const result = await node.validateRemote(ddo) // [!code focus]
```

## Errors

Every call is wrapped, so failures arrive as `OceanNodeError` with the operation named and
the original error kept on `cause`. `IndexingError`, thrown by `waitForIndexer` when the node
recorded an indexing failure, is a subclass.

```ts twoslash
import { OceanNodeError } from '@deltadao/nautilus'

declare const run: () => Promise<unknown>
// ---cut---
try {
  await run()
} catch (error) {
  if (error instanceof OceanNodeError) {
    console.error(error.operation, error.message, error.cause) // [!code focus]
  }
}
```

## Building one directly

You rarely need to — `Nautilus.create` builds it — but the constructor is public.

```ts twoslash
import { OceanNodeClient } from '@deltadao/nautilus'
import { Wallet } from 'ethers'

declare const signer: Wallet
// ---cut---
const node = new OceanNodeClient({
  nodeUri: 'https://ocean-node.dev.pontus-x.eu',
  chainId: 32456,
  auth: signer
})
```

`nodeUri` also accepts a peerId or multiaddr, which switches it to the libp2p transport. A
plain `http://` `nodeUri` on a host other than `localhost`, `127.0.0.1`, `::1` or
`*.localhost` throws an `OceanNodeError`, as in `Nautilus.create`, unless you pass
`allowInsecureTransport: true`; `forEndpoint` applies the same rule to the other node.
